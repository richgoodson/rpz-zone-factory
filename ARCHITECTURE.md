## 30-second summary

```
                 ┌──────────────────┐
                 │  run-rpz.sh      │  POSIX shell orchestrator
                 │  (cron or iact)  │  ──┐
                 └────────┬─────────┘    │ spawns
                          │              ▼
                          │         ┌──────────────────┐
                          │         │  run.py → cli.py │  Python pipeline
                          │         │  (rpz_factory/)  │  fetch → parse →
                          │         └────────┬─────────┘  filter → render
                          │                  │
                          │                  ▼
                          │         /output/.tmp/*.db   (fresh zone files)
                          │
                          ▼
                  ┌───────────────┐
                  │ Per-zone      │ incremental or full-rebuild?
                  │ decision      │
                  └───────┬───────┘
                          │
                ┌─────────┴──────────┐
                ▼                    ▼
         ┌─────────────┐      ┌──────────────┐
         │ incremental │      │ full rebuild │
         │ (nsupdate   │      │ (freeze →    │
         │  + TSIG)    │      │  write →     │
         │             │      │  reload →    │
         │ BIND writes │      │  thaw)       │
         │ .jnl, bumps │      │              │
         │ serial      │      │ Secondaries  │
         │             │      │ AXFR         │
         │ Secondaries │      │              │
         │ IXFR        │      │              │
         └─────────────┘      └──────────────┘
```

**Key insight:** the Python pipeline always writes full zone files to disk.
The shell wrapper decides per-zone whether to apply them via full rebuild
(freeze/reload/thaw) or to diff them against a saved snapshot and apply only
the changes via TSIG-authenticated `nsupdate` (which makes BIND write to the
journal file and bump the SOA serial, which enables IXFR to secondaries).

## The two-layer architecture

There is a strict separation:

1. **Python layer (`rpz_factory/`)** does all the external I/O and
   transformation: fetch feeds, parse them, filter, render zone files.
   It knows nothing about BIND, TSIG, journals, or incremental updates.
   It writes complete zone files to disk and exits.

2. **Shell layer (`run-rpz.sh`)** decides what to do with those zone files.
   It compares them against the previous run's snapshot, applies deltas via
   nsupdate for zones that are configured for incremental updates, and falls
   back to full rebuild + `rndc reload` for everything else.

If you want to change how feeds are fetched, parsed, or filtered — that's
Python. If you want to change how zones are deployed to BIND — that's shell.

**Do not add BIND-specific or nsupdate-specific logic to the Python code.**
It is intentionally a pure pipeline.

## `rpz_factory/` — the Python pipeline

### `__init__.py`
Defines `__version__`. That is all.

### `models.py`

Dataclasses used everywhere. Edit with caution — changes ripple.

- `SourceName` (enum) — canonical source identifiers. Values match the
  filenames in `.cache/`: `abusech_urlhaus`, `cisa_kev`, `spamhaus_drop`,
  `scamsniffer`, `cryptoscamdb`. These are NOT the same as the CLI source
  keys (`urlhaus`, `cisa`, `drop`, etc.) — `cli.py` has two dicts mapping
  between them (`_SOURCE_KEY_TO_NAME` and `_SOURCE_NAME_TO_KEY`). When you
  add a source, update both.
- `EntryType` (enum) — `DOMAIN`, `IP`, or `CIDR`. Determines how the
  renderer encodes the entry.
- `ThreatEntry` — a single blocked thing. `.value` is the raw string;
  `.normalized_value()` lowercases/strips for comparison.
- `FetchResult` — what parsers return: list of `ThreatEntry`, source name,
  optional error, `not_modified` flag for 304 responses.
- `HttpMeta` — `etag` and `last_modified` strings, persisted per source
  in `.cache/<source>.meta.json`.

### `cache.py`

Per-source caching to survive transient source failures. Two distinct
concerns share this file:

1. **Entry cache** — `.cache/<source>.json`. Written on every successful
   fetch. Read when a fetch fails (network error, empty response, parse
   error). Keeps the last-known-good entries so a temporary source outage
   doesn't wipe zones.
2. **HTTP metadata cache** — `.cache/<source>.meta.json`. Holds ETag and
   Last-Modified from the previous response. The fetcher attaches these
   as conditional-request headers next time.

Functions:

- `load_cache(cache_dir, source_enum)` — returns cached `FetchResult` or
  `None`. Wraps JSON read + validation.
- `write_cache(cache_dir, fetch_result)` — atomic write via `.tmp` + rename.
- `load_http_meta(cache_dir, source_enum)` — returns `HttpMeta` or `None`.
- `write_http_meta(cache_dir, source_enum, http_meta)` — atomic write.

### `fetcher.py`

Thin wrapper around `requests.get` with retry, timeout, user-agent, and
conditional-request support. Tracks the last response's headers per URL in a
module-level dict so `cli.py` can extract ETag/Last-Modified after a
successful fetch.

- `fetch_with_conditional(url, etag, last_modified, ...)` — returns the
  `requests.Response`, or raises. Handles 304 by returning a sentinel that
  `cli.py` checks for.
- `get_last_fetch_meta(url)` — returns `HttpMeta` from the in-memory dict,
  populated by the most recent `fetch_with_conditional` call for that URL.

Parsers call `fetch_with_conditional` to get the response, then parse the
body and return a `FetchResult`.

### `filters.py`

Post-fetch filtering to reduce false positives.

- `filter_entries(entries)` — the top-level filter. Applies:
  - **Safe TLDs**: drops any domain ending in `.gov`, `.mil`, `.edu`.
  - **Critical allowlist**: hard-coded list of ~50 infrastructure domains
    (Google, Cloudflare, Amazon, Microsoft, etc.). Dropped with exact or
    subdomain match.
  - **DNS validation**: rejects labels >63 chars, total length >253,
    embedded paths, leading/trailing dots, etc.
  - **Deduplication**: unique by `(entry_type, normalized_value)`.
  - Logs every skipped entry at DEBUG level.

If you want to add or remove false-positive filters, this is the file.

### `parsers/*.py`

One file per source. Each exports a `fetch_and_parse(**kwargs)` function
(except Spamhaus which uses `fetch_drop`) that:

1. Calls `fetch_with_conditional` with the source URL and any passed
   `etag`/`last_modified` kwargs.
2. Parses the response body (JSON / YAML / text RPZ / DROP format).
3. Returns a `FetchResult` with a list of `ThreatEntry`.

To add a new source:
1. Write `parsers/newsource.py` with `fetch_and_parse`.
2. Add its import in `cli.py`.
3. Add it to `ALL_SOURCES`, `SOURCE_FETCHERS`, `_SOURCE_URLS`,
   `_SOURCE_KEY_TO_NAME`, and `SOURCE_ZONE_NAMES` in `cli.py`.
4. Add a `SourceName` enum value in `models.py`.

### `renderers/rpz.py`

Produces RFC 5782 RPZ zone files. One function: `render(entries, zone_name,
ttl, soa_*)`. Output is text with:

- Comment header (source, timestamp, entry count)
- `$TTL` directive
- SOA and NS records at the apex
- For each `ThreatEntry`:
  - `DOMAIN` → `<domain>.<zone>. CNAME .` + `*.<domain>.<zone>. CNAME .`
  - `IP` → `32.<reversed-ip>.rpz-ip.<zone>. CNAME .`
  - `CIDR` → `<prefix>.<reversed-network>.rpz-ip.<zone>. CNAME .`
    (prefixes <24 skipped — BIND RPZ minimum)

**Important for the shell layer:** the extractor in `run-rpz.sh` parses the
exact format this renderer produces. Specifically, it expects:

- One record per line
- The left-hand side followed by whitespace and `CNAME`
- Wildcard twins for domains (skipped during extraction)
- RPZ-IP triggers pass through verbatim as bare keys ending in `.rpz-ip`

If you change the renderer format, re-check `extract_domains_from_zone` in
`run-rpz.sh`.

### `renderers/pihole.py`

Flat domain list for Pi-hole. Only domain entries — IP/CIDR are skipped
because Pi-hole doesn't support them. One domain per line, no zone suffix,
no CNAME.

### `cli.py`

The top-level Python entrypoint. Longest file in the package.

- `build_parser()` — argparse setup. Flags: `--output`, `--zone-name`,
  `--output-file`, `--sources`, `--cache-dir`, `--per-source`, `--allowlist`,
  `-v`/`--verbose`, `--version`.
- `_configure_logging(verbosity)` — sets up logging to stderr.
- `main(argv)` — the actual pipeline:
  1. Parse args
  2. Resolve cache dir (default `{RPZ_DIR}/.cache`)
  3. Loop over requested sources:
     - Load `HttpMeta` from cache
     - Call `fetch_and_parse(etag=..., last_modified=...)`
     - Handle result:
       - **304 not_modified** → load cached entries
       - **Error** → load cached entries, log warning
       - **Empty** → load cached entries
       - **Success** → use new entries, write cache, write HTTP meta
  4. If per-source mode → `_run_per_source(...)` (separate branch)
  5. Otherwise → filter, render, write output file, print summary

- `_run_per_source(...)` — group entries by source, filter each independently
  (no cross-source dedup), render one zone file per source, write to
  `<output_dir>/<zone>.db`. Also handles the allowlist zone (generated from
  the allowlist text file via `_parse_allowlist_file` and
  `_render_allowlist_zone`).

- `_parse_allowlist_file(path)` — read a plain-text allowlist, return list
  of normalized domains. Used only in per-source mode.
- `_render_allowlist_zone(domains, zone_name)` — produces an RPZ zone with
  `CNAME rpz-passthru.` records. This is what the shell extractor operates
  on for the allowlist zone.

**Per-source mode is the production path.** Combined mode still exists for
legacy use but is not what any current deployment uses.

**Key constants in `cli.py`:**

- `ALL_SOURCES` — `["urlhaus", "cisa", "drop", "scamsniffer", "cryptoscamdb"]`
- `SOURCE_ZONE_NAMES` — maps source key to the per-source zone filename
  (e.g., `"urlhaus" → "urlhaus.rpz"`). The shell extractor and the
  `CONF_INCREMENTAL_ZONES` config use these same zone names.
- `_SOURCE_URLS` — feed URL per source (for HTTP meta lookup).
- `_SOURCE_KEY_TO_NAME` / `_SOURCE_NAME_TO_KEY` — bidirectional map between
  CLI source keys (`urlhaus`) and internal `SourceName` enum values
  (`abusech_urlhaus`). Needed because parsers and cache use enum values but
  CLI uses short keys.

## `run-rpz.sh` — the shell orchestrator

POSIX sh. No bashisms. Tested on Debian, Ubuntu, FreeBSD 13+.

### Structure

The file is organized as:

```
1. Configuration (env vars, CONF_* defaults)
2. Sourcing .run-rpz.conf
3. Logging helpers
4. Interactive prompt helpers
5. Usage / CLI parsing
6. Python/venv management
7. Setup wizard
8. Config → CLI args builder
9. BIND tool discovery
10. Incremental (IXFR) helpers         ← v0.6.0
11. Main run function (run_rpz)
```

### Configuration surface

Read the top of `run-rpz.sh` for the canonical list. All `CONF_*` variables
are initialized to empty strings, then overridden by sourcing
`.run-rpz.conf`, then optionally set by the setup wizard, then written back
to the conf file.

Key vars:

| Variable                  | What it controls                                    |
|---------------------------|-----------------------------------------------------|
| `RPZ_DIR`                 | Project directory (where run.py lives)              |
| `PYTHON_BIN`, `VENV_NAME` | Python runtime                                      |
| `RNDC_BIN`                | Path to `rndc`                                      |
| `CONF_OUTPUT`             | `rpz` or `pihole`                                   |
| `CONF_PER_SOURCE`         | `yes` (production) or `no` (legacy combined mode)   |
| `CONF_OUTPUT_FILE`        | Output dir (per-source) or file (combined)          |
| `CONF_SOURCES`            | Space-separated list, or `all`                      |
| `CONF_CHECKZONE`          | `yes` → run `named-checkzone` before deploying      |
| `CONF_COMPILE_ZONE`       | `yes` → compile to raw binary format                |
| `CONF_RELOAD`             | `yes` → reload BIND after successful run            |
| `CONF_ALLOWLIST_FILE`     | Path to allowlist.txt (read by Python + allow.sh)   |
| `CONF_FEEDS_DIR`          | Where `.list.previous` snapshots live               |
| `CONF_TSIG_KEY_FILE`      | TSIG key for nsupdate (shared by allow.sh + IXFR)   |
| `CONF_ALLOW_SERVER`       | nsupdate target server                              |
| `CONF_ALLOW_ZONE`         | Allowlist zone name                                 |
| `CONF_INCREMENTAL_ZONES`  | Space-separated zones that use the IXFR path       |
| `CONF_INCREMENTAL_TTL`    | TTL for nsupdate records (default 300)              |

### Runtime globals (not persisted to config)

| Variable            | What it controls                                  |
|---------------------|---------------------------------------------------|
| `MODE`              | `interactive` (tty) or `cron` (syslog)            |
| `DO_SETUP`          | `1` if `--setup` was passed                       |
| `DO_RELOAD`         | `1` if `--reload-bind ZONE` was passed            |
| `DO_FULL_REBUILD`   | `1` if `--full-rebuild` was passed                |

### Function reference

**Logging (POSIX sh doesn't have log levels, so we cook our own):**

- `log_info` / `log_warn` / `log_err` / `log_notice` — in `cron` mode these
  go to syslog via `logger -t rpz-zone-factory -p daemon.<level> -- "$1"`.
  In `interactive` mode they print to stderr.

**Interactive prompts (only used during `--setup`):**

- `prompt_value label default` — read line, echo result
- `prompt_yn question default` — returns 0 for yes, 1 for no
- `prompt_choice question default opt1 opt2 ...` — numbered menu, echoes
  the chosen option string

**Help / CLI:**

- `usage [exit_code]` — prints the help block and exits
- `parse_args "$@"` — walks `$@`, sets globals, stops at `--` (passing
  anything after through to `run.py` via `RPZ_ARGS`)

**Python runtime management:**

- `check_python_version bin` — verifies `bin` is Python ≥ `PYTHON_MIN_VERSION`
  (currently 3.9)
- `check_venv` — asserts venv dir exists, pip works, `requests` importable
- `create_venv` — creates venv, upgrades pip, installs `requirements.txt`
- `discover_python` — scans PATH for `python3`, `python3.9`..`python3.14`,
  picks the highest version that meets `PYTHON_MIN_VERSION`, displays a
  summary table

**Setup wizard (`run_setup`):**

Interactive walkthrough that sets every `CONF_*` variable. Sections:

1. Environment (RPZ_DIR, Python binary, venv dir)
2. Venv check/create
3. Output configuration (format, per-source, output path, feeds dir,
   allowlist file, sources, verbosity)
4. BIND reload (rndc path, zone to reload, rndc status test)
5. Zone validation and compilation (checkzone, compilezone)
6. TSIG key (shared by allow.sh AND incremental updates)
7. Incremental (IXFR) zones (which zones use the nsupdate path)
8. Save configuration to `.run-rpz.conf`
9. Cron setup (generates crontab line)
10. BIND configuration example (named.conf snippet with allow-update
    stanzas for incremental zones)

After setup, subsequent runs use the saved config and need zero CLI args.

**Config → CLI args:**

- `build_args_from_config` — when no `RPZ_ARGS` were passed, builds them
  from the `CONF_*` vars so `run.py` gets the right flags. In per-source
  mode with checkzone/compilezone enabled, rewrites `--output-file` to
  point at a `.tmp` subdirectory so the old zones aren't clobbered until
  validation passes.

**BIND tool discovery:**

- `find_named_tool tool_name` — searches PATH and common sbin locations
  (`/usr/sbin`, `/usr/local/sbin`, etc.) for `named-checkzone`,
  `named-compilezone`. Echoes the path or returns empty.

### Incremental (IXFR) helpers (v0.6.0)

These are the v0.6.0 additions. Read them together — they form a
self-contained subsystem.

- `incremental_cname_target zone_name` — echoes the correct CNAME target
  for a zone. `allowlist.rpz` → `rpz-passthru.`; everything else → `.`
  (NXDOMAIN). If you add a new "passthru" type zone, extend the case.

- `is_incremental_zone zone_name` — returns 0 if `zone_name` appears in
  `CONF_INCREMENTAL_ZONES` (space-separated list), 1 otherwise.

- `extract_domains_from_zone db_file zone_name` — awk-based parser. Reads
  a rendered RPZ zone file and emits one bare domain per line, sorted,
  unique. Wildcard twins are stripped; SOA/NS/comments/directives are
  skipped. RPZ-IP triggers (`N.reversed-ip.rpz-ip.<zone>.`) pass through
  verbatim as bare keys ending in `.rpz-ip` — they round-trip through
  nsupdate but never get a wildcard twin (handled in `build_nsupdate_batch`).

  **If you change the renderer output format in `rpz_factory/renderers/rpz.py`,
  you must re-check this extractor.**

- `build_nsupdate_batch zone adds_file dels_file out_file` — writes an
  nsupdate input script to `out_file`. Format:
  ```
  server <CONF_ALLOW_SERVER>
  zone <zone>
  update delete <domain>.<zone>. CNAME
  update delete *.<domain>.<zone>. CNAME    ← skipped for .rpz-ip keys
  ...
  update add <domain>.<zone>. <ttl> IN CNAME <target>
  update add *.<domain>.<zone>. <ttl> IN CNAME <target>    ← skipped for .rpz-ip
  ...
  send
  ```
  Deletions come first so a re-add registers as a net change in the
  journal. Inner helper `_emit_update op bare` detects `.rpz-ip` keys and
  skips the wildcard twin.

- `run_incremental_for_zone zone new_db_file` — the core incremental path.
  Returns 0=success, 1=fatal error (caller falls back to full rebuild),
  2=seed required (no `.previous` snapshot).

  Steps:
  1. Preflight (TSIG key, nsupdate binary, feeds dir exists)
  2. If `<feeds>/<zone>.list.previous` missing → return 2 (seed needed)
  3. `rndc sync <zone>` — flush in-memory journal to `.db` file so the
     snapshot comparison is accurate (decision point #3 in the design
     conversation)
  4. `extract_domains_from_zone` → `<feeds>/<zone>.list.current`
  5. `comm -13 prev curr` → additions
  6. `comm -23 prev curr` → deletions
  7. Log the counts (`adds=N dels=M`)
  8. Empty diff → clean up `.current`, return 0 (no-op)
  9. `build_nsupdate_batch` → temp file
  10. `nsupdate -k <TSIG_KEY> < batch` — apply
  11. On success: rotate `.current` → `.previous`, `rndc sync <zone>` to
      flush the new journal entries to `.db`, clean up temp files
  12. On failure: log error, keep temp files for post-mortem, return 1

  **No churn threshold.** Trusts nsupdate (decision #4 in the design
  conversation). If a massive delta is too much for nsupdate, it will
  fail, we catch the failure, and fall back to full rebuild.

- `seed_feed_snapshot zone db_file` — writes the initial
  `<feeds>/<zone>.list.previous` from a freshly rendered zone file. Called
  after a full rebuild for a zone that is configured as incremental, so
  that the NEXT scheduled run can diff against this baseline. This is how
  a zone transitions from "seed" to "incremental" without any manual step.

### Main run function (`run_rpz`)

Called by `main` when `--setup` wasn't passed. The flow:

1. Validate project dir and `run.py`
2. Build `RPZ_ARGS` from config if not passed
3. Check Python + venv (auto-create if missing)
4. Run `run.py` under venv, log stderr
5. On success, branch on `CONF_PER_SOURCE`:
   - `yes` → the **multi-phase per-source path** below (production)
   - `no`  → **combined-mode path** (legacy, kept for compatibility)

**Multi-phase per-source path:**

This is the most important part of the script. Read it carefully before
changing.

```
Phase 1: Validate
  For every *.db in <output>/.tmp:
    Run named-checkzone. Zones that fail are removed from _valid_zones.
    (They are NOT deployed. Live zones are untouched.)

Phase 2: Sort into buckets
  For each validated zone:
    If --full-rebuild was passed        → _full_bucket
    Else if not in CONF_INCREMENTAL_ZONES → _full_bucket
    Else if TSIG missing                → _full_bucket (with warning)
    Else if .previous snapshot missing  → _full_bucket (seed)
    Else                                → _incremental_bucket

Phase 3: Apply incremental zones (BIND stays live)
  For each zone in _incremental_bucket:
    run_incremental_for_zone
      0 → success, compile raw zone file onto .db path
      2 → seed required (defensive; shouldn't happen after Phase 2
          pre-checked); route to full bucket
      * → failed; route to full bucket

Phase 4: Full rebuild prep
  If _full_bucket has any zones AND DO_RELOAD:
    rndc sync -clean    # flush all journals
    rndc freeze          # freeze all dynamic zones

Phase 5: Full rebuild writes
  For each zone in _full_bucket:
    Compile .db from .tmp using named-compilezone -F raw (if enabled)
    Otherwise cp .tmp/<zone>.db → <output>/<zone>.db
  Remove orphaned .jnl files ONLY for zones in _full_bucket.
  NEVER touches .jnl files for zones in _incremental_bucket — those
  journals are live and BIND is actively using them.

Phase 6: Reload and thaw
  For each zone in _full_bucket:
    rndc reload <zone>
  rndc thaw    # resume dynamic updates for all zones

Phase 7: Seed snapshots
  For each zone in _full_bucket that IS configured as incremental:
    seed_feed_snapshot → writes .previous from the fresh .db
  So the next run can take the incremental path.

Phase 8: Cleanup
  Remove <output>/.tmp
  Log summary: zones=X incremental=Y full=Z
```

### The combined-mode path

Much simpler and not used in production. Renders a single `.db` file,
optionally validates and compiles it, reloads a single zone. This code
path is preserved verbatim from v0.5.0 and has NOT been touched in v0.6.0.
Do not delete it — tests and legacy docs still reference it.

### `reload_bind`

Used only by the combined-mode path. `rndc reload <RELOAD_ZONE>`.

### `main`

Calls `parse_args`, branches on `DO_SETUP`, calls either `run_setup` or
`run_rpz`, exits with the return code.

## `allow.sh` — real-time allowlist management

Standalone script for operators. Adds or removes a single domain from the
allowlist zone **immediately** (without waiting for the next scheduled
`run-rpz.sh` run).

### How it fits in

- The allowlist is a plain text file (default:
  `${CONF_FEEDS_DIR}/allowlist.txt`). One domain per line, `#` comments.
- `allow.sh` is the interactive interface to that file. It edits the file,
  then applies the same change live to BIND via `nsupdate`.
- `run.py` reads the same file via `--allowlist` during scheduled runs and
  renders it into an allowlist RPZ zone.
- `run-rpz.sh`'s incremental path diffs the rendered allowlist zone against
  `.previous` on each run, same as any other incremental zone. If `allow.sh`
  already applied a change live, the scheduled run's diff will show the
  domain as "new" and attempt to re-add it via nsupdate; BIND treats this as
  idempotent (no SOA bump if the record already exists). Small chatter, no
  functional problem.

### Order of operations

For `allow.sh example.com`:

1. Preflight (nsupdate, TSIG key, rndc, allowlist file path)
2. `allowlist_add` — append domain to allowlist file (atomic, skips if
   already present)
3. `nsupdate_add` — send `update add` + wildcard `update add` for
   `example.com` with `CNAME rpz-passthru.` to the allowlist zone
4. **On nsupdate failure:** revert the text file edit via `allowlist_remove`
   (decision #2 in the design conversation — keeps text file and live zone
   in sync)
5. On success: `rndc sync -clean <zone>` to flush journal, write audit log
   entry

Remove is symmetric.

### Key functions

- `validate_domain` — RFC-shape checks on the input
- `preflight` — verifies nsupdate, TSIG key file exists, rndc, allowlist
  file path is set
- `allowlist_add file domain` — append if not present
- `allowlist_remove file domain` — atomic line removal via temp file
- `nsupdate_add domain zone` / `nsupdate_remove domain zone` — compose and
  send the nsupdate batch with TSIG
- `rndc_sync_clean zone` — flush and clean journal
- `audit_write action domain result` — append to `allow-audit.log`
- `audit_show lines` — `tail -n` the audit log with a header

### Config sourcing

`allow.sh` sources `.run-rpz.conf` at startup and picks up these vars:
- `CONF_TSIG_KEY_FILE`
- `CONF_ALLOW_SERVER`
- `CONF_ALLOW_ZONE`
- `CONF_ALLOWLIST_FILE` (with fallback to `${CONF_FEEDS_DIR}/allowlist.txt`)

Flags override config, config overrides built-in defaults.

## Configuration files

Generated by `run-rpz.sh --setup`. Sourced at the top of `run-rpz.sh` and

1. Declare it at the top of `run-rpz.sh` with an empty default
2. Add a prompt in `run_setup`
3. Add it to the `cat > "$_conf_file" <<CONF` heredoc that writes the file

Auto-created by `cache.py`. Contains:

- `<source>.meta.json` — HTTP ETag/Last-Modified per source

Safe to delete at any time; next run will re-fetch and rebuild.

## Design decisions worth knowing

These came up during v0.6.0 design and are baked into the code. If you
disagree with them, that's fine, but know they were deliberate:

1. **Python writes full zone files every run.** We do NOT skip rendering
   even when nothing changed. Reasons: (a) we always have a fresh baseline
   on disk for recovery; (b) the conditional-HTTP layer in `cache.py`
   already saves the expensive part (the network fetches); (c) simpler.

2. **Per-zone opt-in for incremental.** `CONF_INCREMENTAL_ZONES` is a list,
   not a global boolean. Lets operators migrate zones one at a time.

3. **On any nsupdate failure, fall back to full rebuild for that zone
   only.** Other zones continue with their chosen path. This is what the
   multi-phase loop in `run_rpz` implements.

4. **`rndc sync` runs TWICE per incremental zone per run.** Once before
   the diff (to reconcile on-disk state with any dynamic updates that
   happened between scheduled runs, e.g. from `allow.sh`) and once after
   (to flush the new deltas back to disk). Disk I/O cost is fine; keeps
   `.db` files current for debugging and BIND restart recovery.

5. **No churn threshold for falling back to full rebuild.** Trusts
   nsupdate. If a batch is too big nsupdate will fail, we catch the
   failure, and fall back. Simpler than guessing a threshold.

6. **Seed path is automatic.** First time a zone runs as incremental, or
   any time `.previous` is missing, the shell takes the full-rebuild path
   and then seeds the snapshot. There is no manual "first run" step.

7. **Never delete `.jnl` files for incremental zones.** They are BIND's
   authoritative state for dynamic zones. The old v0.5.0 code removed all
   orphaned journal files after the zone write phase; the v0.6.0 code
   only removes journals for zones in the full-rebuild bucket.

8. **`allow.sh` reverts text file edits on nsupdate failure.** So the
   text file (which `run.py` reads on the next scheduled run) always
   matches the live zone state.

9. **Single TSIG key for both allow.sh AND incremental updates.** Rich
   confirmed all dynamic zones accept the same key. Simpler than tracking
   per-zone keys.

10. **Combined mode is preserved but not used in production.** Don't
    remove it. It simplifies the code path for anyone who wants a single
    zone and doesn't care about per-source attribution.

## How to test changes

Local (dev machine, no BIND):

```sh
# Syntax check both shell scripts
sh -n run-rpz.sh && sh -n allow.sh

# Exercise the Python pipeline without writing zones
./run.py --output rpz --zone-name test.local -v --output-file /tmp/test.db

# Test the setup wizard flow
./run-rpz.sh --setup

# Test extract_domains_from_zone manually
# (copy the awk block into a standalone script and feed it a .db)
```

On the remote BIND host:

```sh
make deploy                        # rsync current branch
cd ~/rpz-zone-factory

# Dry run without incremental
./run-rpz.sh -i                    # should behave like v0.5.0

# Enable incremental for one zone to start
./run-rpz.sh --setup               # set CONF_INCREMENTAL_ZONES=urlhaus.rpz

./run-rpz.sh -i                    # first run: seeds urlhaus.rpz
./run-rpz.sh -i                    # second run: should take incremental path
                                   # logs: Incremental[urlhaus.rpz]: adds=N dels=M

# Check BIND state
rndc zonestatus urlhaus.rpz        # serial should NOT bump if diff was empty
dig @localhost <known-bad>.urlhaus.rpz CNAME
cat /var/log/syslog | grep rpz-zone-factory

# Force a full rebuild (recovery mode)
./run-rpz.sh -i --full-rebuild
```

When you're confident, expand `CONF_INCREMENTAL_ZONES` to all zones and
watch secondary IXFR traffic in the BIND query log to confirm they're only
transferring deltas.

## Things that are NOT implemented but could be

In priority order, if anyone wants to extend this:

1. **Post-incremental zone-file compile as an atomic rename.** Currently
   `named-compilezone -o <final> ...` writes directly to the final path.
   Not atomic. For large zones a reader could see a half-written file.
   Write to `.tmp` first, then `mv`.

2. **Per-zone `rndc freeze`/`thaw` instead of server-wide.** The current
   code freezes EVERYTHING when any zone needs a full rebuild. If you have
   non-RPZ dynamic zones on the same server, this could disrupt them.
   `rndc freeze <zone>` is per-zone but the iteration adds complexity.

3. **Metrics emission.** Would be nice to Prometheus-textfile-export
   counts of adds/dels per zone per run. Easy to bolt onto the
   `log_info "Incremental[$_zone_name]: ..."` line.

4. **Parallel nsupdate.** For very large diffs, splitting additions and
   deletions across multiple nsupdate invocations could speed things up.
   Complicated by ordering (deletes must happen before adds for re-adds
   to register in the journal).

5. **Per-source zone config** — right now the renderer hardcodes the
   source → zone-name mapping in `SOURCE_ZONE_NAMES`. Making that
   configurable would let operators split/merge zones at will.

6. **Integration tests.** None currently exist. The shell layer
   especially would benefit from a test harness that spins up BIND in
   a container.
